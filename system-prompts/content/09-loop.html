01

O loop

Iterar não é “testar prompts até um número subir”. É um experimento com uma variável por vez, uma hipótese escrita e uma decisão registrada antes do resultado.

Congele o eval

Prompt, modelo, temperatura, parser, golden set e versão do split. Se uma dessas coisas muda entre duas medições, você não está comparando prompts.

Analise o erro por cluster

Agrupe por par (verdade, previsto), não por caso engraçado. “Quatro duvida_produto viraram status_pedido” é um diagnóstico; “olha esse aqui” é uma anedota.

Escreva a hipótese

Uma frase causal: “falta uma definição que separe processo de pedido específico”. Se a hipótese não gera uma mudança observável, ainda não é hipótese.

Faça a mutação mínima

Uma regra, um conjunto de exemplos, uma mudança de contrato. Se precisar mexer em duas coisas, declare que são independentes e pré-registre as duas comparações.

Meça no dev, pareado

Mesmos casos, mesmo alvo. Compare as decisões caso a caso, não só a média. O teste pareado pergunta “quais casos mudaram e em que direção?”.

Mantenha ou reverta

Registre o que mudou, o que quebrou e por quê. Um revert também é resultado: evita que a próxima pessoa repita o mesmo caminho.

Antes de culpar o prompt, classifique o erro. Cada tipo tem um conserto diferente — e metade deles não se conserta no prompt.

O caso: quatro versões, três hipóteses

A Loja Norte não "melhorou o prompt". Fez três mutações, cada uma respondendo a um cluster diferente. O dev subiu de 67,0% para 93,2%; o test, de 62,9% para 93,5%.

O v1 confunde duvida_produto com status_pedido nos dois sentidos: quatro casos para cada lado no dev, quatro e três no test. "Garantia", "prazo" e "rastreio" puxam a classe errada. As definições da v2 atacam essa fronteira; no total, corrigem 11 casos no test sem quebrar nenhum. Só três desses 11 são essa fronteira específica — o resto vem de prioridade, contraexemplos e da política de outros. A maior célula de erro no dev cai de 4 para 3.

A v2 ainda erra fronteiras que já têm definição, mas não têm exemplo - e o contrato JSON ainda adiciona superfície de erro. A v3 adiciona cinco few-shots escolhidos para o limite e troca JSON por label plano. Seis casos corrigidos, zero quebrados; a maior célula cai de 3 para 2. A v4 adiciona exemplos de injection, inglês e mensagens curtas, e endurece a política de outros. Corrige três casos (uma fronteira, um defeito, um inglês) e quebra um (um caso de rastreio): o saldo líquido é +2, não uma vitória estatística.

Esse é o ponto que a média esconde: a v4 não é “3,2 pp melhor”. É “três consertos e um novo erro”. Em 62 casos, isso pode ser sorte.

03

O ganho é real?

Comparar dois prompts rodando sobre os mesmos casos exige um teste pareado. O teste de McNemar (teste estatístico para decisões pareadas do tipo acertou/errou) ignora os empates e olha apenas os casos em que os dois prompts discordam.

Monte uma tabela 2×2: chame de b os casos que o prompt B consertou (A errava e B acertou) e de c os que B quebrou (A acertava e B errou). Os casos que ambos acertam ou ambos erram não ajudam a desempatar. Se os dois prompts forem equivalentes (hipótese nula), cada discordância funciona como um cara ou coroa justo (50% para cada lado). Quando a soma b + c é pequena, calcule o valor-p pela distribuição binomial exata:

McNemar · binomial exata, dois lados
p = min(1, 2 · Σ C(b+c, i) · 0,5^(b+c)), para i ≤ min(b, c)

v1→v2: b=11, c=0  → p ≈ 0,001
v2→v3: b=6,  c=0  → p ≈ 0,031
v3→v4: b=3,  c=1  → p = 0,625

Ter p=0,625 não prova que “não houve melhoria”. Significa apenas que uma amostra de 62 casos não tem fôlego para separar um ganho de 3,2 pp do puro acaso. A v4 pode até ser melhor, mas os dados ainda não provam isso. Chamar o resultado de “promissor” é honesto; cravar “comprovado” não é. Mesmo no dev, a diferença entre v3 e v4 não atinge significância estatística: 4 casos corrigidos contra 1 quebrado geram p≈0,375.

duas armadilhas

Bootstrap pareado é uma alternativa: reamostre os casos, calcule o Δ em cada reamostra e veja se o intervalo cruza zero. Múltiplas comparações são o outro risco: testar dez mutações e escolher a melhor infla o falso positivo — o winner's curse. Pré-registre a comparação primária ou corrija o limiar.

04

Quando parar

Parar não é desistir. É reconhecer que a próxima mutação custa mais do que o erro que ela remove.

Congele quando: (1) duas rodadas seguidas não movem a fronteira de Pareto — nenhum ganho sem quebrar outra coisa; (2) o orçamento de tempo ou de chamadas acabou; (3) todos os clusters restantes são rótulos ambíguos que humanos também errariam; (4) os erros que sobram são ruído de rótulo, não de prompt.

A v4 ainda comete quatro erros no test: dois na fronteira entre classes (057 e 064), um em tentativa de injection (144) e um em mensagem curta e ambígua (150). Nem tudo ali é ruído inevitável — ainda daria para lapidar. Mas o ganho marginal já ficou pequeno e o risco de estragar casos que hoje passam é alto. A decisão mais sensata é congelar a versão, rodar o test uma única vez e subir em canary (liberação gradual para uma pequena fração do tráfego) com rollback automático, medindo o comportamento em produção.

definição operacional de congelado

Hash do prompt, versão do modelo, temperatura, parser e golden set registrados. Sem isso, “congelado” é memória. O canary não é uma segunda opinião: é a mesma pergunta com mais casos e consequência real.
