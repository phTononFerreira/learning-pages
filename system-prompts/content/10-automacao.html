01

O que automatizar

Automatizar prompt não é pedir a um modelo “melhore este texto”. É gerar candidatos e escolhê-los contra uma métrica fixa. Sem a métrica, o otimizador produz texto plausível — não uma decisão melhor.

O ciclo manual da página 09 é a sua linha de base. Qualquer otimizador automático precisa superar a sua análise de erros — não apenas bater um prompt inicial mal escrito. Se a ferramenta não entrega mais do que você conseguiria ajustando o prompt à mão no mesmo dev, o mérito veio das milhares de tentativas extras, não do algoritmo.

ALVO 1

Instruções

Regras, definições e ordem. APE e OPRO geram candidatos de instrução; MIPRO combina instruções e demos. É o alvo mais barato de testar e o mais fácil de diluir.

ALVO 2

Demonstrações

Quais exemplos entram, em que ordem, com que rótulo. DSPy faz bootstrap de demos a partir dos casos que o programa acerta. Mais exemplos não é melhor; cobertura de fronteira é.

ALVO 3

Estrutura

Etapas, retries, parser, fallback. Isso não é prompt: é programa. Se o erro é de formato, nenhum otimizador de texto conserta o parser.

02

DSPy e GEPA no caso de 7 classes

A tarefa da Loja Norte cabe em uma Signature: mensagem entra, uma das sete rotas sai. O dev de 88 casos vira train/val; o test de 62 fica fora do compile.

No DSPy, o próprio tipo do campo define o contrato: um Literal com os sete labels. A métrica compara igualdade exata (exact-match) e o otimizador enxerga apenas o conjunto de dev. Você aponta o modelo-alvo uma única vez via LiteLLM: dspy.LM("bedrock/amazon.nova-lite-v1:0"). Já o GEPA vai além da nota numérica: ele lê um feedback em texto explicando cada erro, reflete sobre a falha e mantém uma fronteira de Pareto com os melhores prompts candidatos. O salto de 75,4% para 87,0% em ~1.643 chamadas de métrica vem do tutorial facility support do DSPy (10 categorias multi-label, 68 exemplos, GPT-4.1 nano), e não do artigo original do GEPA. Trate esse número como ordem de grandeza, não como promessa para o nosso caso de 7 classes.

O modelo-alvo não muda. Você até pode usar um modelo maior para a reflexão — ele apenas analisa os erros e propõe regras, sem substituir o classificador final. Mas se você avaliar os candidatos no Nova Pro e colocar o vencedor para rodar no Nova Lite, o ganho evapora na troca. Ao terminar, exporte o prompt compilado, leia o texto final gerado e rode a sua suíte de avaliação sobre ele. Salvar o artefato do framework não garante que o prompt renderizado por baixo do capô seja limpo.

from typing import Literal
import dspy

LABELS = ("saudacao", "duvida_produto", "status_pedido",
          "reclamacao", "cancelamento", "falar_humano", "outros")

class Intent(dspy.Signature):
    """Classifique a mensagem em exatamente uma rota."""
    mensagem: str = dspy.InputField()
    rota: Literal["saudacao", "duvida_produto", "status_pedido",
                  "reclamacao", "cancelamento", "falar_humano", "outros"] = dspy.OutputField()

program = dspy.Predict(Intent)   # sem CoT: latência baixa

def exact_match(example, pred, trace=None):
    return pred.rota == example.rota

dspy.configure(lm=dspy.LM("bedrock/amazon.nova-lite-v1:0"))

from dspy.teleprompt import MIPROv2
optimizer = MIPROv2(metric=exact_match, auto="light")
compiled = optimizer.compile(program, trainset=trainset, valset=valset)

compiled.save("router_optimized.json")   # exporte, renderize e revalide

trainset e valset saem dos 88 casos de dev. O test de 62 nunca entra no compile.

import dspy

def metric(example, pred, trace=None):
    ok = pred.rota == example.rota
    fb = "correto" if ok else f"esperado {example.rota}; veio {pred.rota}"
    return dspy.Prediction(score=float(ok), feedback=fb)

gepa = dspy.GEPA(
    metric=metric,
    auto="light",
    reflection_lm=dspy.LM("bedrock/amazon.nova-pro-v1:0", temperature=1.0),
    num_threads=8,
    track_stats=True,
)
compiled = gepa.compile(program, trainset=trainset, valset=valset)

03

O loop DIY

Com 88 casos de dev, você não precisa de um framework para começar. Precisa de um loop que não se engane: uma mudança por rodada, comparação pareada e uma única olhada no test.

pseudocódigo · loop de busca
eval = freeze(golden.dev)                 # 88 casos, prompt, modelo, parser
base = run(eval, prompt_v1)
clusters = group_by(base, key=(true, pred))

for round in range(6):
    cands = [apply(prompt, m) for m in propose(clusters, n=5, llm=strong)]
    outs  = [run(eval, c) for c in cands]
    delta = paired_bootstrap(outs, base)       # IC do Δ, caso a caso
    front = pareto(outs, axes=(accuracy, broken_cases, tokens))
    keep(front)                            # não escolha o topo da média
    clusters = group_by(best(front), key=(true, pred))

test_once(best(front))                     # uma olhada, regra já escrita

O passo que quase todo mundo pula é o filtro de pareto. Um prompt candidato que sobe 1 pp na média geral mas passa a errar três casos de cancelamento não é estritamente melhor — ele só trocou um erro por outro. A fronteira de Pareto preserva apenas os candidatos imbatíveis em pelo menos um eixo (maior acurácia, menos regressões ou menor custo em tokens). Depois, o bootstrap pareado verifica se a diferença sobrevive à reamostragem dos casos, enquanto o teste de McNemar faz a mesma checagem olhando direto para as discordâncias.

04

Custo: a conta que ninguém faz

O custo de otimizar é chamadas × tokens × preço. O custo de não otimizar é humano. A conta só fecha quando os dois entram na mesma mesa.

estimativa de chamadas e custo
calls ≈ exemplos × candidatos × rodadas
custo = calls × (in_tokens × preço_in + out_tokens × preço_out) / 1M

100 × 5 × 6 = 3.000 chamadas (cenário hipotético; o dev tem 88)
3.000 × (900 × 0,06 + 30 × 0,24) / 1M = $0,1836 ≈ $0,18

O número parece pequeno. Mas ele é só o alvo. A reflexão do otimizador roda em um modelo forte: 20 chamadas com 8.000 tokens de entrada e 2.000 de saída no Pro custam 20 × (8.000 × 0,80 + 2.000 × 3,20) / 1M = $0,256 — mais que os $0,18 do alvo. O GEPA light fica na faixa de 1,5–2,5 mil metric calls; o tutorial DSPy usou ~1.643. Some tudo antes de dizer “é barato”.

a regra do alvo fixo

Otimizar com um modelo grande e implantar um pequeno é trocar o experimento no meio. O prompt aprende atalhos do modelo que escreveu — e o alvo não os tem. Fixe modelo, versão e parâmetros; se o alvo migrar (Nova Lite 1.0 → Nova 2 Lite), revalide antes de reaproveitar o prompt.

05

Quando não automatizar

Otimizador é amplificador. Se o sinal de entrada é fraco, ele amplifica o ruído com mais elegância.

Não automatize quando: você tem menos de 50 exemplos rotulados; não existe métrica determinística; o eval não está congelado; a tarefa muda toda semana; latência ou custo dominam a decisão; ou a taxonomia ainda está se movendo. Nesses casos, error analysis manual vence — e vence rápido, porque você ainda está descobrindo o que medir.

Também não automatize para consertar formato. Se a saída vem com preâmbulo, JSON truncado ou caixa errada, o conserto é parser, validação e retry. Um otimizador de instruções pode até aprender a evitar o preâmbulo, mas você pagou caro por um problema de código.

pré-requisito mínimo

Golden set congelado, métrica que você confia, modelo-alvo fixo e pelo menos 50–100 exemplos. Sem os quatro, o loop manual não é o plano B: é o plano A.
